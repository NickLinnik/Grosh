## Slice 15f: Shared `build_where` helper for optional-filter SQL assembly

## Slice 17: Rebuild Monobank transfer detection per the v2 ADR

**Design:** Replace the existing single-file `MonobankTransferDetection` strategy and its tier-specific repo queries with the module layout specified in `references/adr-transfer-detection-v2.md` and the "Transfer detection (Monobank strategy)" subsection of `technical-considerations.md`. The new strategy runs one universal candidate fetch, applies a hard IBAN consistency filter, classifies per-pair evidence (`bilateral`/`unilateral`/`none`), and decides via a count-and-decide branch with the bucket-locked principle. It writes `metadata.layer.transfer.{row, pair?}` on every MCC 4829 row through a new `metadata_block` field on `TransferResult`, which the orchestrator merges via the structured per-layer merge function landed in Slice 16.

**Why a full rebuild instead of an in-place refactor:**
1. The module shape inverts. v1's three near-identical tier methods + interleaved anomaly literals + SQL glue have no incremental path to the 8-module split (`detector` orchestrator + pure-function helpers `flags`, `iban_classifier`, `decision`, `metadata`, `anomalies` + repo + descriptions). Almost nothing transplants.
2. The SQL fully changes. `find_unclaimed_partner_tier_a/b/c` collapse into one `find_universal_candidates` with a two-clause amount predicate and a different result-handling contract.
3. The `metadata.layer.transfer` block is a new write surface; intermediate states between the two designs would be Frankenstein code with no clean test boundary.

## Slice 18: `category` + `exclude_category` list filters on `GET /transactions`

Replaces the existing single-value `special_category: SpecialCategory | None` query param on `GET /transactions` with two complementary repeated-key list params:

- `category: list[SpecialCategory] | None` — whitelist. SQL adds `AND special_category = ANY($N::special_category[])`. NULL `special_category` rows are excluded (NULL is never `= ANY(...)`).
- `exclude_category: list[SpecialCategory] | None` — blacklist. SQL adds `AND (special_category IS NULL OR special_category != ALL($N::special_category[]))`. The `OR IS NULL` clause is load-bearing — without it, NULL `NOT IN (...)` evaluates to UNKNOWN and silently drops ordinary rows. Frontend's main-feed use case is `?exclude_category=transfer`.

Router validates the conflict rule (`set(category) & set(exclude_category)` non-empty → 422) before any DB call. Functional spec §2.6 and technical-considerations.md "**SpecialCategory filter on `GET /transactions`**" subsection are the contracts.

**Breaking change to API surface.** The single-value `special_category` param is removed. No shipped frontend depends on it (spec 004 is Draft).
